## 5. 建议处理顺序

依赖关系决定顺序，不按严重度简单排序。

**第一步：先让门禁恢复绿色（D-1 → D-3）**
D-1 的 E501 是一行改动即可修复的确定性缺陷，修完后重跑 `make lint` 才能让 `mypy` 与 `architecture-check`（116 项）拿到真实结论；随后按 `pnpm run commit`（git-cz）把 G-03/04/05 与验收文档分组落库。**没有这一步，后面所有改动的可信度都没有门禁背书。**

**第二步：判定 D-2 的归因（在正常开发机复跑后端套件）**
若 22 项失败消失 → 记录为核验环境限制，但应把 `rule_examples.TIMEOUT_SECONDS = 6` 的余量问题单列为鲁棒性改进项（慢机器与 CI 会复发）；若失败复现 → 升为 P0，规则与校验链路必须先修，否则第 4 步规则环节不可用。

**第三步：补验收闭环（B-10 → C 组）**
B-10 的"完整 12 步零 API"E2E 是报告的核心验收命题，也是 C 组多项 `❔` 的收敛手段——把 12 步写成 spec 后，C-1/C-6/C-7 可顺带转成实测结论。建议与 C-3（远程库实测）分开排期，后者需要外部环境。

**第四步：资产治理细节（B-2～B-6、B-9、E-2）**
这组互不依赖，可并行：继承环校验与维护域唯一约束是后端小改动；关系详情页、属性详情补列是前端小改动；属性级转换链与审计端到端需要先定数据模型。

**第五步：剩余形态与增强（A-1～A-3、B-7、B-8、E-1）**
G-22 需要区间条渲染、G-29 需要多源贡献数据模型，成本高于 A-3；E-1 的完整 OWL-DL 属长期项，接入前应保持 A08 = NOT_RUN，不得显示为通过。
