## 5. 建议处理顺序

依赖关系决定顺序，不按严重度简单排序。

**第一步：先让门禁恢复绿色（D-1 → D-3）**
D-1 的 E501 是一行改动即可修复的确定性缺陷，修完后重跑 `make lint` 才能让 `mypy` 与 `architecture-check`（116 项）拿到真实结论；随后按 `pnpm run commit`（git-cz）把 G-03/04/05 与验收文档分组落库。**没有这一步，后面所有改动的可信度都没有门禁背书。**

**第二步：D-2 已定性，不再是待办（复核即可）**
D-2 的 22 项失败是本机 `rule_runner` 6 秒超时的**既有基线**（本机技能 `knowledge-repo-verify` 已记载同一根因），不是本轮改动引入的缺陷。**不要**去放宽 `TIMEOUT_SECONDS` 或 `RLIMIT_CPU`——那是刻意的 bounded/offline 安全设计。若要一份干净的全量结果，需在机器空闲时（`uptime` load < 10）单独重跑 `test_m4_rules.py`。

**第三步：补验收闭环（B-10 → C 组）**
B-10 的"完整 12 步零 API"E2E 是报告的核心验收命题，也是 C 组多项 `❔` 的收敛手段——把 12 步写成 spec 后，C-1/C-6/C-7 可顺带转成实测结论。建议与 C-3（远程库实测）分开排期，后者需要外部环境。

**第四步：资产治理细节（B-2、B-5 剩余、B-6、B-9、E-2）**
这组互不依赖，可并行：关系详情页、属性详情补列是前端小改动；改名同步、属性级转换链、数据属性的基数/数值约束/来源条款需要先补模型与迁移；审计端到端是测试补强。

**第五步：剩余形态与增强（A-2、B-7、B-8、E-1）**
A-2（G-29 融合解释图）需要"多来源贡献 / 冲突值"的数据模型，成本最高；B-7 画布直接建模、B-8 小地图是前端增强；E-1 的完整 OWL-DL 属长期项，接入前应保持 A08 = NOT_RUN，不得显示为通过。
