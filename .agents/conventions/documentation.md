# 功能文档同步规范

本规范由2026-11-26用户明确要求建立，适用于当前知识中台仓库。产品行为以当前实现和实际验证为依据；本文是文档同步要求的唯一规范来源，README、贡献指南、完工自检和PR模板只引用。

## 1. 变更前定位

读取[功能台账](../../docs/product/feature-catalog.md)与[功能登记](../../docs/product/features.json)，确定稳定功能编号、实现、测试、指南和关联模块。新增功能分配新编号；删除或停用功能说明去向，不复用旧编号。

同一编号可以覆盖一组有共同用户目标的操作。API、后台处理、权限限定入口及详情页也需登记，不能只按主菜单统计。

## 2. 哪些变化需要同步

| 代码或产品变化                         | 必须检查的文档                                               |
| -------------------------------------- | ------------------------------------------------------------ |
| 功能新增、调整、停用                   | 功能台账、机读登记、对应用户指南、产品范围                   |
| 路由、导航、操作顺序                   | 工作台与导航、模块指南、快速入门、功能入口登记               |
| 角色、授权、登录与重置                 | 角色权限、账户指南、部署初始化、故障排查                     |
| 接口、状态、校验、错误                 | 模块指南、限制与排错、OpenAPI生成契约；不复制全部字段        |
| 模型、版本冻结、迁移、兼容             | 架构、模块台账、操作指南、迁移与恢复说明                     |
| 配置、依赖、启动、部署命令             | 中英文README、部署、配置、开发指南与样例说明                 |
| 已知限制新增或解决                     | 限制清单、受影响功能、验证记录和对外表述                     |
| 仅内部重构、测试维护或无可感知行为变化 | 核对来源路径与验证依据是否失效；确无需文档更新时给出具体理由 |

“修复”也可能改变用户可见行为，不能按提交类型自动免除文档检查。不得以修改无关Markdown满足要求。

## 3. 内容与证据

- 面向产品、用户、运维和开发分别组织；README保留定位、启动和导航，不重复所有细节。
- 标明核验日期、Git基线与未提交工作区范围；不把包版本、历史报告或临时预览称为正式发布。
- 实现状态与验证状态分别记录；测试存在、源码确认、实际执行和浏览器实测不得混写。未验证写明原因。
- 功能文档必须说明角色、前置条件、操作、结果、限制和常见失败，保留真实权限、状态与冻结语义。
- 示例使用虚构数据；不公布真实口令、令牌、客户数据或密钥。隔离测试账号不能当作默认部署账号。
- 历史ADR/验收报告保留时间语义，通过当前说明和归档索引消除误导；第三方许可原文和生成文档不随意重写。

## 4. 提交前检查

```sh
pnpm run check:docs
pnpm run check:docs:staged
```

结构检查验证维护文档的本地链接与锚点、功能编号、源码/测试/指南路径、现有页面及API模块覆盖。暂存模式读取Git索引，避免未暂存的文档替暂存代码“通过”。新增文件应一起暂存。

提交钩子在 lint-staged 后执行暂存检查。不存在的链接、遗漏的页面/API模块和无效登记阻止提交；影响报告中的 `REVIEW_REQUIRED` 提醒进行语义核对，不自动证明或否定内容正确。

任何 `REVIEW_REQUIRED` 都必须由实现者在PR或交付中逐项归并说明：更新了哪些关联文档，或为什么不需要更新。审查者核对理由与实际差异。当前机制不自动解析自然语言或保证人/Agent遵循规则，不宣称具备完全自动语义同步能力。

登记以模块和功能为粒度；同一API模块内新增端点可能不触发覆盖错误，仍需人工检查契约差异。复杂动态路由结构变更也要同步检查脚本的路由提取方式。

## 5. 验证与交付

文档修改至少执行结构检查、相关格式检查并核对命令和内容。检查脚本变更执行定向行为测试；业务变化按既有测试规范执行。纯文档不要求重复全量业务测试，但文档声称实测的内容必须有实际证据。

每次交付包含：受影响功能编号、用户可感知变化、更新的文档、实际验证和未验证项。没有文档影响时明确写出具体范围与理由，不能只写“无”。需要发布或外部系统验证的内容继续遵守对应授权边界。
